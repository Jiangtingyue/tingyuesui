My role · 我负责什么

我负责产品定义、架构选择、交互和视觉设计、版本规划和验收。代码由 Claude Code 和 Codex 编写，我负责分配任务和检查结果。

Problems · 解决的问题

开发中遇到了四个主要问题。

Problem 0101

长对话遗忘

对话变长以后，早期内容会被忘掉。

聊得太久的部分，整理成一段段带出处的摘录，回复前在整段对话里找相关的记忆。每条记忆都能找到原始消息。

Problem 0202

记忆混淆

模型会把自己说过的话当成用户说的。

按说话人分开存储，用户和模型的内容不再混在一起。

Problem 0303

情绪影响记忆

一次情绪波动会长期影响后面的对话。

情绪和事实分开存放，情绪不写入长期记录。

Problem 0404

费用过高

对话变长以后，每轮费用跟着上涨，而且看不到明细。

优化缓存，命中率 91.8%。费用按对话和后台分开显示。

Motion · 设计与动效

开屏像折叠屏一样展开。

开屏参考了折叠屏打开的那一下：合着的磨砂屏幕先停在窗口中间，准备好以后滑到左边、右半块翻开，磨砂慢慢退掉，露出首页。页面切换、卡片和按钮也做了一套弹性动效。

How it works · 一条消息的旅程

从按下发送到回复出现，一条消息会经过这些地方。

01

按下发送

消息从聊天界面交给本机的后端。界面用 SwiftUI 重做过，发消息和接收回复仍由藏在界面下面的原网页完成。这部分逻辑已经跑稳，重做界面时没有跟着重写。

02

原样存档

这句话先原封不动地存进原文档案。之后的所有记忆，都记着它的消息编号。

03

找相关的记忆

后端在三处同时查：整个窗口的总账、用户说过的事实、最近的对话要点。限时 3 秒，超时就用本地的保底查找。

04

对回原话

找到的事实要和原消息逐字核对，原话的校验值也要对上。对不上的，不会带进这一轮。

05

拼成这一轮的提示词

系统提示、人设和历史对话每轮基本不变，放在前面走缓存；找到的记忆放在最后。这也是缓存命中率能到 91.8% 的原因之一。

06

发给模型

只把这一轮需要的内容发出去。House 接了 6 种模型服务，可以随时切换。回复回到聊天界面。

07

后台整理

回复显示出来以后，这条消息进入后台队列，整理成总账里的要点和原子事实。程序中途退出也不会丢。

这套记忆只用用户说过的原话，每一条都能查到出处。

设计取舍

  • 只在当前这段对话里查找

  • 主聊天不用向量检索

Transparency · 看得见的 Prompt

每一轮发给模型的内容，
都能打开核对。

我做了一个 Prompt 控制台。每一轮实际发给模型的系统提示、人设、记忆和上下文都能在这里看到，哪些被带进去、哪些被裁掉也会标出来。系统提示和人设可以直接在这里改。

服务商在接口之后自己加的规则，本机读不到，我就标成“不可见”。

少写提示词

长的人设指令在长对话里效果会变弱。我的做法是让角色自己说出身份，再用记忆系统持续提供一致的信息。这样换了模型，角色性格也能保持。

角色设定的三种载体

Carrier 01 · 第三方视角

人事档案

一个虚构组织的内部网站。包括个人信息、训练经历、工作记录和权限等级。用公文的写法，提供角色本人没有说过的信息。

Carrier 03 · 交互视角

情境小游戏

像素风的小游戏。玩家陪角色逛超市，做出选择。四项数值会随选择变化，数值的设置也体现了角色性格。

Behavior · 用行为写角色

设定里多写角色具体做的事，少用形容词。比如用“他给挑食的猫买指定的猫粮”来代替“他很细心”，模型拿到的信息更具体，长对话里角色也更稳定。

Negative space · 写清楚不会做的事

除了写角色会做什么，也写清楚他不会做什么。这样可以减少模型变成普通助手的语气。
